# M7 — Integrations, part 1: slskd (Soulseek via slskd)

_Written 2026-11-24 on `feature/m7-slskd` (from `842384c`). Upstream reference: kima-hub `main`
`b927e307e451c208d03a9509595af57ba399f28e` (read-only checkout)._

## Scope and owner decisions

- Integrations ship in the **standard build** (no cargo feature), but every integration is
  **disabled by default** and makes no network request until an admin configures and enables it.
  This replaces the roadmap's older "each integration behind a cargo feature" note.
- **slskd before native Soulseek.** The native P2P client (upstream `lib/soulseek/client.ts`,
  `p2p-client.ts`) and Lidarr come later.
- Integration settings and secrets are **server-wide, admin-only** (main profile of an admin
  account, the existing `AdminUser` rule), stored in the existing `settings_kv` table; secrets use
  the existing `Cipher` (AAD `settings_kv:<key>`, HKDF key derivation unchanged). No new plaintext
  store, no new crypto.
- Personal requests (who asked for an album, request history) are **profile-owned** and land with
  the download slice, keyed by `profile_id` from creation (M-PROF rule).
- Downloads land under `MUSIC_PATH` only, with strict path safety and no accidental overwrite.
- Reserved ids: divergences **D-291..D-299**, migrations **0067..0069** (current max `0066`;
  older migrations and checksums are never modified).

## Task 1 — slskd configuration and connection check ✅ (this slice)

**Inputs.**

- `GET /api/system-settings` (admin) adds `soulseekEnabled` (default `false`), `slskdUrl`
  (`""` when unset), `slskdApiKey` (always `""`) and `hasSlskdApiKey`.
- `POST /api/system-settings` (admin) accepts `soulseekEnabled` (boolean), `slskdUrl`
  (string/null; `""` or `null` clears; otherwise a plain `http`/`https` origin — no credentials,
  path, query or fragment, ≤ 512 characters; stored without a trailing slash) and `slskdApiKey`
  (`""` keeps, `null` clears, trimmed, ≤ 200 characters, visible US-ASCII only — `!`..`~`, no
  spaces, tabs, CR/LF, DEL, other controls or non-ASCII; the connection check applies the same
  rule to a typed key). The whole body is validated before anything is stored; errors never quote
  the input.
- **The key is bound to the URL it was saved with** (review I-1). When a save changes the
  normalized URL — replaced, set from empty or cleared — the stored key is deleted unless the same
  body carries a fresh valid key; `""` or an absent key is not fresh, `null` clears. An equivalent
  URL (scheme/host case, default port, trailing slash) is not a change. The current URL is read
  from the table, not the cache, and the URL/key pair is written in one transaction under a
  transaction advisory lock (serializing competing pair saves, key-only ones too, also while no
  row exists); a failed write changes neither. The cache is refreshed after the commit. Other
  settings in the same body keep their existing per-key writes.
- `POST /api/system-settings/test-soulseek` (admin) with optional `mode` (only `"slskd"`),
  `slskdUrl`, `slskdApiKey`. URL: the body's, else the stored one, else 400 `slskd URL is
  required`. Key: the body's, else the stored key **only when the URL equals the stored URL**.
  Not saved; does not require `soulseekEnabled`.

**Answers.** 200 `{"success":true,"message":"Connected to slskd","isConnected":true}`; 502
`{"error": ...}` with one of `slskd is not connected to the Soulseek network`, `slskd rejected
the API key` (401/403), `slskd did not answer` (connect failure, DNS, TLS, timeout), `slskd
answered unexpectedly` (other status, redirect, non-JSON, > 64 KiB); 400 for invalid bodies; 409
`Outbound connections are turned off` when the network guard refuses the host or the process has no
outbound client.

**Intended limits (the SSRF boundary).** The configured URL may be a private LAN address on
purpose (admin-approved). The check sends exactly one `GET /api/v0/application`, follows no
redirect, uses no environment proxy, has a 10 s timeout, reads at most 64 KiB, sends the key only
in the `X-API-Key` header (never in the URL), and never forwards it to another address.
`AETHER_NET_DENY_REAL=1` refuses any non-loopback host before connecting (no panic, no DNS).
Saving or reading settings contacts nothing; there is no startup or background job.

**Not in this slice.** Search, downloads, the acquisition pipeline, `canAcquire` (stays `false`),
the native client, Lidarr, any frontend UI, the onboarding Soulseek step (still the existing
placeholder), `soulseekMode` storage.

**Evidence.** `aether-net --test slskd` (13, no database; local stand-in server), `aether-api
--test slskd_settings` (11, SQLx on the isolated test cluster; local stand-in server),
`auth_profiles` admin-route tests (2), the unchanged `system::*` settings tests (7) and
`aether-db --test settings_kv` (6). A real slskd instance was **not** contacted (none installed).

**Review fix (I-1 key/URL binding, M-1 key validation; independently re-reviewed).** `aether-net --test
slskd` 15/15 (RED 14/1), `aether-api --test slskd_settings` 18/18 (RED 14/4: the four leak/atomicity

## Task 2 — search over slskd (D-292)

**Upstream contract (inventoried at `b927e30`).** `routes/mountAccess.ts` mounts `/api/soulseek`
for any signed-in user (only `POST /connect` and `/disconnect` are admin; only `POST /download`
needs the acquire permission). `routes/soulseek.ts`:

- `POST /api/soulseek/search` behind `requireSoulseekConfigured` (403 `{"error":"Soulseek
  credentials not configured. Add username/password in System Settings."}`); body `{query}` or
  `{artist, title}` (query = `"<artist> <title>"`), else 400 `{"error":"Either 'query' or both
  'artist' and 'title' are required"}`; answers `{"searchId": <uuid>, "message": "Search started"}`
  at once and searches in the background (10 s), keeping results in an in-memory session owned by
  the caller (5-minute TTL, at most 50 sessions, the oldest evicted) and streaming them over SSE
  (`search:result`/`search:complete`).
- `GET /api/soulseek/search/:searchId` → `{"results": [...], "count": n}`; a missing, expired or
  foreign session is 404 `{"error":"Search not found or expired","results":[],"count":0}`.
- One result per unlocked file: `{username, path, filename, size, bitrate, format, parsedArtist,
  parsedAlbum, parsedTitle}` — `filename` is the last path part (either slash), `format` `flac` by
  extension else `mp3`, `parsedArtist`/`parsedAlbum` the third/second-last path parts,
  `parsedTitle` the file name without extension and leading track number, `bitrate` =
  `round(size·8 / (length·1000))` when both are known, else 0 (`slskd-client.ts`).
- slskd wire (`slskd-client.ts` `search`): `POST /api/v0/searches` `{searchText, responseLimit:
  100}` → `{id}`; every 1 s `GET /api/v0/searches/{id}/responses` (array of `{username,
  hasFreeUploadSlot, uploadSpeed, queueLength, token, files: [{filename, size, length, sampleRate,
  bitDepth, isLocked}]}`, first response per user kept) then `GET /api/v0/searches/{id}`
  (`isComplete` ends it); `DELETE /api/v0/searches/{id}` afterwards, errors ignored.

**This slice (backend only, no UI, no migration, no SSE).** The same two routes and shapes for a
signed-in profile, gated by `soulseekEnabled` **and** a stored valid `slskdUrl` (upstream's
slskd-mode check is the URL alone). The URL and its bound key are captured once per search from one
settings snapshot. Sessions are owned by the **profile** (another profile, even of the same
account, gets the 404). Limits: query ≤ 200 characters (400), `responseLimit` 100, at most 1000
files per search, slskd answers ≤ 64 KiB (create/status) and ≤ 1 MiB (responses), 10 s total
deadline, 5 s per request, 1 s poll interval, at most 2 searches in flight per process (a third is
429, not queued), 50 sessions × 5 minutes. Every request goes through the network guard, no
redirects, no proxy, one client per search; the search id must be a UUID before it is put into a
fixed path. The remote search is deleted after completion, error or timeout (one bounded 5 s
attempt), and from a drop guard when the search task is cancelled (process shutdown). Errors are
fixed texts; query, key, URL, user and file names are never logged. `GET` adds `"complete":
<bool>` (no SSE yet). Downloads, `canAcquire` (stays `false`), `/status`, `/connect`,
`/disconnect`, `/download` and the UI are later tasks.

**Evidence (local, not reviewed).** `aether-net --test slskd_search` 9/9 (RED: E0432, the API did
not exist; one test expectation corrected from `Complete` to the planned `Capped`), the unchanged
health tests `aether-net --test slskd` 15/15 after the shared client/body helpers refactor,
`aether-api --test slskd_search` 8/8 (RED 0/7 with the routes absent; the sibling-profile case was
added after the implementation and proved by a mutation that dropped the owner check: 2/2 owner
tests failed, then restored), `aether-api --lib soulseek::tests` 1/1 (upstream title regexes,
including U+0085), `aether-api --test slskd_settings` 18/18 (run before a final private
rename/format in the search code; the health path is untouched by it), clippy `-D warnings` on
both crates' libs and the three test targets, `cargo fmt --all --check`. Real slskd: **not run**
(none installed); the wire is taken from upstream source and checked only against a loopback
stand-in.

**Review fix (I-1, untrusted text amplification; re-review pending).** The body caps bound one
poll, not what a result row repeats: a ~1 MiB peer name in a 1 MiB answer with 1000 tiny files
would be cloned into every row (~1 GiB per session, 50 sessions). The adapter now checks peer text
when decoding, before storing the user as seen, cloning or calling back: a username must be
non-blank and ≤ 255 UTF-8 bytes, else that peer's whole response is skipped; a filename (the full
peer path) must be non-blank and ≤ 1024 UTF-8 bytes, else that file alone is skipped and its valid
siblings are kept. Nothing is truncated; a skipped file does not count against the 1000-file cap;
the search still ends `Complete`/`TimedOut`/`Capped` as before and the remote search is still
deleted. With these bounds a result row holds at most 255 + 4 × 1024 = 4351 bytes of text (path;
leaf or, for an empty leaf, the whole path; artist, album and title are parts of the path), so one
session keeps ≤ 4,351,000 bytes (≈ 4.15 MiB) of text and 50 sessions ≈ 207.5 MiB, plus struct and
JSON-escaping overhead while serializing (computed with Python; the old worst case was ≈ 48.8 GiB).
No separate output budget was added. Evidence (private): `aether-net --test slskd_search` RED
9/13 (the four new tests failed on the old adapter) → GREEN 13/13; unchanged `--test slskd`
15/15, `aether-api --test slskd_search` 8/8 (guarded runner), `aether-api --lib soulseek::tests`
2/2 (new row-bound test over five worst-case path shapes), clippy `-D warnings`, `fmt --check`.

Review I-1 closed by parent code review of `90d328f`: validation precedes deduplication and callbacks,
invalid files are skipped before the file cap, and no truncation or cleanup change was introduced.
Parent reran the search adapter tests on `b19272d`: 13/13, exit 0. No remaining Critical/Important
findings in the reviewed slice; real slskd and hosted CI for Task 2 are still pending.

**Known limits** (recorded for the reviewer; none is silently accepted as an owner decision).
1. A process shutdown cancels a running search; its drop guard spawns the `DELETE`, but the
   runtime may stop before it is sent. If the create answer is lost after slskd created the
   search, its id is unknown and the remote search cannot be deleted (slskd keeps it until its own
   cleanup).
2. Evicting one of the 50 sessions does not cancel its search task; that task keeps its permit
   (at most 2) until it ends (≤ 15 s). The budget is concurrency only (2), not upstream's
   30-per-220-s window.
3. A search occupies its admission slot for up to 10 s of work plus 5 s of cleanup (≤ 15 s).
4. `complete: true` with no results can also mean a failed search (network or a refused key):
   there is no SSE and no error field yet (UI, Task 5).
5. A settings change does not cancel a search already started from the captured URL/key
   snapshot; it runs out within 15 s.
6. Kids profiles can search (upstream: any signed-in user); the policy is for Task 4 (acquire
   permission) and is not owner-accepted.

Results appear per poll (≤ 1 s), not streamed. Sessions are lost on restart. The existing open
choices (GET `complete` instead of SSE, 429 instead of queueing) stay open.

## Task 3 — download path safety (D-293) 🟡 primitive implemented, awaiting review

A synchronous library primitive, `aether_library::ingest` (`crates/aether-library/src/ingest.rs`),
with no route, job, database or network use yet. It is **not** the download pipeline: Task 4 calls
it (through `spawn_blocking`) once slskd reports a finished file.

**Contract.**

- `FileName` (one component) and `RelPath` (non-empty, `/`-separated) are validated, never
  repaired: empty, `.`/`..`, `/`, `\`, NUL or any control character, a drive prefix (`C:`), more
  than 255 bytes, or the reserved `.aether-ingest-` prefix is refused; `RelPath::parse` also refuses
  absolute, UNC and doubled/trailing separators. `remote_file_name` takes only the basename of an
  untrusted Soulseek path (either slash) and refuses it if malformed. Making names out of metadata
  (sanitizing) is the caller's explicit step, not done here.
- `ingest_file(src_root, src, dest_root, dest, Limits { max_bytes, expected_size }, &cancel)`;
  `copy_into` takes any `Read` instead of a source file. Roots must be absolute existing folders
  with no symlink anywhere in their path (opened once with `openat2(RESOLVE_NO_SYMLINKS)`).
- Source: `openat2(root_fd, RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS)`,
  `O_NOFOLLOW | O_NONBLOCK`, regular file by `fstat` (folder/FIFO/device refused). Hard links are
  accepted (the copy is a new inode). The source is only read, never moved or deleted, and may be
  on another filesystem.
- Destination folders: created and reopened one component at a time from the root descriptor with
  the same resolve flags, so any symlink (escaping, internal or dangling) or file in the way is
  refused. Folders created before a later failure stay (empty).
- Copy: 64 KiB buffer; at most `max_bytes`, one byte more is `TooLarge` (a stream, not metadata);
  `expected_size`, when given, must match exactly; cancellation is checked before every chunk.
  Returns byte count and SHA-256.
- Commit: `.aether-ingest-<uuid>.part` in the target folder (`O_CREAT | O_EXCL`), fsynced, then
  `renameat2(RENAME_NOREPLACE)`, or `linkat` + `unlinkat` where the filesystem lacks it; with
  neither, `Unsupported` (no check-then-rename). An existing file, folder or (dangling) symlink at
  the target is `AlreadyExists`; the folder is fsynced after the commit.
- Failure, cancellation or panic removes only this call's own part file by exact name; other
  `.part` files are never touched and there is no sweep.

**Deliberately not ported** (upstream `services/soulseek.ts` at `b927e30`): `fs.rename(part, dest)`
replacing an existing file, automatic `title (n)` collision naming, and the hourly sweep deleting
stale `.<uuid>.part` files. A collision is an explicit error here; automatic renaming waits for an
owner decision with Task 4.

**Not covered.** A local user who owns the roots can still rename whole folders while a copy runs
(the write stays in the opened folder, whose name is theirs); live symlink-swap races are prevented
by construction but not race-tested; the `linkat` fallback is not exercised (the test filesystem
supports `RENAME_NOREPLACE`). Linux only (elsewhere `Unsupported`).

**Verification (scoped).** `cargo test -p aether-library --test ingest`: 18/18 (validators;
nested copy with hash; existing file/folder/symlink/dangling targets kept; destination parent
symlinks inside and outside the root; source and source-parent symlinks; FIFO/folder/missing
source; hard link; exact cap; oversize stream; size mismatch both ways; read failure and
cancellation cleanup with foreign `.part` files kept; 8 concurrent writers to one name, exactly
one wins; root policy). Behavioural RED: 14/18 failed against a naive `std::fs` version.
Sensitivity: removing `RENAME_NOREPLACE`, the destination or source resolve flags, the root
symlink flag, the byte cap, the part cleanup or the regular-file check each fails its targeted
tests (7/7), source restored by hash. Stable fmt/clippy `-D warnings` on the crate's lib and this
test target only. No slskd, network or database involved.
